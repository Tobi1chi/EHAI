## 为什么

11-04 用户在桌面窗口试用时有四处卡住：

- 选了一个不是 Git 仓库的文件夹，连续三次失败，只能自己到终端运行 `git init`；
- 权限要逐项填写（命令、Shell、Git），默认什么都不开，Planner 只能回答“没有命令可以验证”；
- 新建线程要先选工作区、选项目、写目标、再写说明；
- 首页是一列文字，看不出哪些事情要处理、哪些正在推进。

用户要的是：和一个个人 Agent 对话，由它代为填写；页面是一块工作台，卡片一眼看清，点开看细节。

## 决定（产品经理，2026-11-04，用户授权）

| 项 | 决定 |
| --- | --- |
| 非 Git 文件夹 | 不再直接报错。登记接口返回可识别的错误码，页面弹窗说明后由用户确认一键初始化：`git init` 并把现有文件做成首个提交；仓库已存在但没有提交时只补首个提交；选中的是仓库子目录时提示改用根目录 |
| 权限 | 三档访问级别，含义仿照 Codex：**只改文件**、**改文件并运行命令**（默认）、**完全访问**；“自定义”保留现有逐项设置。级别可在设置里随时更改，只影响之后批准的 Run |
| 个人助手 | 工作台内置一个助手角色（经 Hub 与 Pi 调用模型，和 Planner 分开）。它能读取工作台状态、新建线程、把用户的话转给 Planner；批准方案、开始执行、授予权限、通过人工检查只给出按钮，由用户点击 |
| 工作台 | 工作首页改为卡片看板：需要处理 / 进行中 / 已完成，工作区与便签各成一组；右侧（窄屏在顶部）是助手。卡片点开进入现有线程页 |

外部顶层 Agent 仍可经 CLI/MCP 使用核心，内置助手不是它的替代，也不拥有数据库状态。

## 模块 1：一键初始化 Git

用户结果：选任意文件夹都能添加成功，代价只是确认一次。

- `POST /api/v1/workspaces/from-folder` 新增 `initialize_git: bool = false`。
- 不满足条件且 `initialize_git=false` 时返回 422，`error.code` 区分三种情形：
  `folder_not_git_repository`、`folder_without_commits`、`folder_not_git_root`（消息中给出根目录）。
- `initialize_git=true`：不是仓库则 `git init`；没有提交则 `git add -A` 后提交 `chore: initialize repository`
  （空文件夹为空提交）。提交身份用用户 Git 配置；没有配置时用 `EHAI <ehai@localhost>`，并在结果中说明。
  子目录情形不初始化，仍返回 `folder_not_git_root`。
- `ehai add --init-git` 走同一函数。
- 选中路径与磁盘写法只差大小写（macOS 默认大小写不敏感）时视为同一文件夹，按 Git 给出的根路径登记（11-04 修复）。
- 失败行为：`git` 命令失败时原样报告 stderr 摘要，不留下半初始化状态以外的改动（`git init` 已完成时不回滚）。

## 模块 2：访问级别

用户结果：添加工作区时选一档；Planner 和 Worker 知道能做什么。

| 级别 | `access` | Worker 能做 | 对应现有设置 |
| --- | --- | --- | --- |
| 只改文件 | `files` | 读写自己 worktree 里的文件，Git 只读 | `git_permissions=[git.read]` |
| 改文件并运行命令（默认） | `commands` | 再加在 worktree 里用 Shell 运行测试、脚本、安装依赖 | 再加 `available_shells=[本机 Shell]` |
| 完全访问 | `full` | 再加在自己的 worktree 里 Git 提交 | 再加 `git.local_write` |
| 自定义 | `custom` | 逐项设置 | 现有字段 |

- 本机 Shell：macOS 优先 `zsh`，Linux `bash`，Windows `pwsh` 或 `powershell`，取 PATH 上第一个存在的。
- 命令直接在本机运行，**不做网络或文件系统沙箱**（与 Codex 的沙箱不同）；页面写明这一点。
  推送远端、危险 Git 操作不在任何一档里，仍归用户。Reviewer 始终只读。
- 级别由设置推导，不另存；与任何一档都不相同即为 `custom`。
- `PUT /api/v1/workspaces/{id}/access {access}`：改写登记并重启该工作区；有活动 Run 或规划时返回 409，
  不打断执行。已批准 Run 的执行配置不变，按现有规则在开始新 Run 时核对。
- `ehai add --access files|commands|full`，默认 `commands`；给了 `--allow-command/--shell/--git-permission` 时为自定义。

## 模块 3：个人助手

用户结果：在首页说一句话就能开始一件事、问进度、回答 Planner、记下或改掉一条生活待办，不用填表。

- 角色：管理器内的 `assistant` 角色，经 Hub 启动 Pi 会话，只开放下列工具；没有 Pi 自带的文件、命令或网络工具，
  终端只经 `run_command`（11-04 第三轮加入）。
  每条用户消息是一次独立会话，最近的对话记录作为上下文传入（不续用原生会话）。
- 工具：

  | 工具 | 作用 | 是否直接执行 |
  | --- | --- | --- |
  | `read_workbench` | 工作区（路径、状态、访问级别）、线程（状态、更新时间）、待办数 | 读 |
  | `read_thread` | 一条线程的状态、最近讨论、草稿方案摘要、Run 状态、待办 | 读 |
  | `start_thread` | 在指定工作区建线程：复用或新建项目，写目标，后台发起规划讨论 | 是（规划不改代码） |
  | `message_planner` | 把用户的话发进某条线程的讨论（后台进行） | 是 |
  | `run_command` | 在某个工作区文件夹（或用户主目录）运行一条终端命令 | 只读命令直接运行；其余由用户在弹窗里点“运行” |
  | `read_life` | 生活项目里未完成的待办（按到期时间排序，最多 100 条）和最近完成的 5 条 | 读 |
  | `add_life_tasks` | 把用户要记下的 1–20 条待办（标题、可选到期时间）存进生活项目 | 是（同「录入」自己输入，不再二次确认） |
  | `update_life_task` | 改一条生活待办的状态（完成、取消、重开）、标题或到期时间 | 是 |
  | `reply` | 结束本轮：回复文本和可选按钮（打开线程、添加文件夹、打开生活待办） | — |

- 授权边界：批准方案、开始 Run、添加文件夹（会授予权限）、人工检查、整合与建分支，助手只能给按钮或链接；
  按钮由用户点击，经现有接口执行。终端命令见下文“终端命令”。
- 接口：`GET /api/v1/assistant` 返回对话；`POST /api/v1/assistant/messages {text, life}` 跑一轮并返回回复；
  `POST /api/v1/assistant/reset` 清空对话。同一时间只跑一轮，忙时 409。对话保存在 `EHAI_HOME/assistant/`。
- 只答文字：模型没调用 `reply` 而以文字结束时（DeepSeek 下多次出现），把它最后一段文字当作本轮回复送达，不带按钮；
  其余角色仍要求结束工具。这不是重放：本轮已调用的工具只执行过一次，且已记入对话（11-04 修复）。
- 失败行为：模型或 Hub 失败时，这一轮记为失败并显示原因，不自动重发；`start_thread` 已建的线程保留并在回复里给出链接。
- 只在 `ehai up` 启动的管理器上可用（需要引擎配置的模型）。

### 生活待办（11-04 第四轮）

用户结果：对助手说“明天中午提醒我报名羽毛球活动”就记成一条明天 12:00 到期的待办，也能问“我有哪些待办”、
说“猫粮买好了”“改到下午三点”。

- 生活项目：生活区用哪个项目是这个浏览器的设置（`设置` 或生活区首次进入时选择或新建），核心没有区域标记。
  页面每次发消息都带上 `life: {workspace_id, project_id}`（未选为 `null`），管理器存在 `EHAI_HOME/assistant/life.json`，
  批准命令后的续答轮沿用它。三项工具只作用于这个项目；`update_life_task` 拒绝不属于它的待办。
  未选生活项目时工具返回 `no_life_project`，助手给“打开生活”按钮，页面带用户到选择或新建处。
- 记录：`add_life_tasks` 走与「录入」相同的 `life.capture` 工作流，`require_confirmation: false`（用户自己说的话，
  同在录入页自己输入）；原话作为 `source_text` 随记录保存。`due_at` 须为带 UTC 偏移的 ISO 8601，
  上下文给出 `local_now`（本机时区）供模型换算“明天中午”；没说具体时间时由模型假定并在回复里说明。
- 修改：`update_life_task` 先读当前版本，再按 `UpdateLifeTaskRequest` 整体替换；参数为 `null` 表示不变，
  `clear_due: true` 清除到期时间。版本冲突照常返回错误，不自动重试。
- 提醒的边界：EHAI 不在到期时发闹钟或系统通知，到期待办出现在生活区「今天」。助手保存提醒时说明一次。
- `start_thread` 不会把工作线程建进当前生活项目（也仍跳过名为“生活”的项目）。

### 终端命令（11-04 第三轮）

用户结果：让助手查看仓库或跑一条命令时不用切到终端；会改动东西的命令先经用户点头，像 Claude Code 的权限弹窗。

- 自动运行（只读）须同时满足：命令在只读清单内（`ls pwd cat head tail wc stat du tree grep rg find which whoami uname date`，
  以及 `git status/log/diff/show/rev-parse/ls-files/blame/describe/shortlog`，`git branch/tag/remote` 只带列出参数）；
  没有管道、重定向、`;`/`&&`、`$`、反引号、通配符（grep/rg/find 的模式除外）；不带会执行或写入的参数
  （如 `find -exec/-delete`、`rg --pre`、`git -c`、`--output`、`tail -f`）；在已登记的工作区文件夹里运行，
  且参数里的路径解析后不出这个文件夹（`~`、绝对路径、`..` 越界都不行）。不经 shell，直接按词执行，20 秒超时。
- 其余命令（写文件、安装、构建、测试、脚本、联网、shell 语法、在工作区外或主目录）记为待批准：助手本轮说明用途后结束；
  页面在输入框上方显示命令、目录、需要批准的原因和“运行 / 拒绝”。点“运行”后用本机 Shell（zsh/bash/pwsh）原样执行，
  600 秒超时，然后助手自动接着这条结果再答一轮；点“拒绝”只记下拒绝。同一时间最多一条待批准；用户发了新消息则该条作废。
- 命令在本机直接运行，没有网络或文件系统沙箱，页面写明这一点。输出合并标准输出与错误，只保留最后 12000 字，
  经凭证脱敏后保存并交给模型；子进程继承管理器环境变量，`PAGER`/`GIT_PAGER` 设为 `cat`。
- 每条命令（含自动运行的）都作为一条对话记录显示：命令、目录、是否自动、状态、退出码，输出可展开。
  管理器在命令运行中停止时，重启后记为“结果未知”，不重跑。
- 接口：`POST /api/v1/assistant/commands/{command_id}/approve` 与 `…/deny`（空对象 body），返回整段对话；
  不在待批准状态时 409，命令不存在 404，忙时 409。

## 模块 4：卡片工作台

用户结果：打开首页就知道该做什么；细节点开再看。

- 布局：桌面宽度两栏，左侧看板、右侧助手（固定高度、内部滚动）；窄屏助手在上、看板在下。
- 看板分组：**需要你处理**（待办与等待批准的方案，强调色）、**进行中**（规划中/执行中）、**已完成**（折叠，显示最近几条）、
  **工作区**（访问级别、状态、添加按钮）、**便签**。
- 卡片：标题最多两行、状态标签、所在工作区与项目、更新时间、下一步提示；整卡可点，进入线程页。
- 视觉：统一 8px 间距栅格，卡片内边距 20px、间距 16px、内容区最大宽度 1280px；边框更淡，层次靠留白和字重，
  不靠线条；深浅色主题沿用现有 token。

## 执行记录

### 2026-11-04 第一版

实施与设计的差异：`folder_not_git_root` 不在错误中附根目录字段，根路径写在消息里；工作台没有单独的“便签”数据源
（核心的便签是 Planner 问题，已在待办中），卡片本身即便签；助手通知（Planner 消息未确认送达、本轮失败）
只存错误码与技术细节，文案由页面给出。

验证（macOS，隔离 EHAI_HOME，端口 18766，真实 DeepSeek `deepseek-flash`）：

- 静态检查、mypy（含 win32）、import 契约、Schema 与 TS Client 重新生成、页面构建通过；产品 E2E 1 passed。
- 仓库外临时诊断：普通文件夹、无提交仓库、空文件夹各自得到对应错误码，确认后均有首个提交；子目录始终为 `folder_not_git_root`。
- API：非 Git 文件夹先 422，`initialize_git=true` 后 ready、默认 `commands`（zsh、git.read）；
  `PUT …/access {full}` 后重启为 ready，执行配置为 zsh + `git.read`/`git.local_write`、无列出命令。
- 页面：工作区卡片打开设置，改为“运行命令”约 10 秒完成重启；添加第二个非 Git 文件夹弹出确认，确认后登记。
- 助手：第一轮建出线程（约 4 秒），Planner 在后台讨论并给出待批方案；追问进度时如实说明 Planner 尚未回复；
  经页面发送的第三轮建出另一条线程并提醒前一条方案待批准。回复中曾出现内部代码 `review_plan`，提示已禁止此类代码。
- 浅色/深色与平板宽度下布局检查；窄屏助手在上方，高度限制在约半屏。

未覆盖：助手 add_folder 按钮、通知失败提示、Worker 在各访问级别下的真实执行、桌面窗口内实跑、Windows。

### 2026-11-04 第二轮

用户看过页面后提出三项：

| 反馈 | 处理 |
| --- | --- |
| 增加删除工作区 | 工作区设置底部“移除工作区”，需要确认；`ehai remove <id>`；管理器 `POST /api/v1/workspaces/{id}/remove`。有未结束 Run（含暂停）或活动规划时拒绝。不动用户文件夹，核心数据移到 `manager/removed/<id>-<时间>/`，不删除；文件夹已不存在的工作区（如被手动删掉的）也能移除 |
| 右下角不要显示太多东西 | 理解为助手输入框：去掉快捷键说明行，占位文字只留“想做什么？”，发送改为圆形图标按钮，单行起、随内容增高；Enter 发送、Shift+Enter 换行（输入法组字时不发送）。对话开始后不再显示助手标题下的说明 |
| 自动回答改用 OpenAI Decisions | 快环 Connector 从 Jev 换成 OpenAI Decisions，见[双反馈环实验](../DECISIONS.md) |

验证（隔离 EHAI_HOME，端口 18766）：页面移除一个文件夹已被删除的工作区，登记与卡片消失、数据在 `removed/` 下；
批准并开始一个 Run 后经 API 与 CLI 移除均返回 409，工作区保持 ready；把归档移回并重新添加同一文件夹后原线程恢复；
`ehai remove` 对已登记的新仓库成功且文件夹不变，对不存在的 ID 返回 404。输入框在 1440 宽下单行显示，
Shift+Enter 换行、Enter 发出，助手（真实 DeepSeek）正常回复。未覆盖：移除时 `git worktree prune` 对真实 Run 留下的
worktree 的效果、桌面窗口内实跑、Windows。

### 2026-11-04 第三轮：终端命令

用户要求助手能操控终端，只读以外的命令要像 Claude 那样弹窗由用户手动运行。实施见上文“终端命令”。

验证（隔离 EHAI_HOME，端口 18766，真实 DeepSeek `deepseek-flash`，经页面）：

- 仓库外临时诊断：35 条命令的判定与设计一致（只读的 `git status`、`grep -rn 'a|b' .`、`find . -name '*.py'` 自动；
  管道、重定向、`find -exec`、`git -c`、`git branch 新名字`、`cat ~/.zshrc`、`cat ../x`、`$HOME` 等需批准）。
- “demo 里 git 状态怎么样”：自动运行 `git status`、`git log --oneline -10`，回答与仓库一致。
- “跑一下测试”：先自动 `ls -la`、`cat calc.py`，发现没有测试后先问；同意后弹出 `python -m pytest -q` 的批准卡片，
  点“运行”后退出码 5（没有测试）。**发现**：接着的那一轮模型把正确答复写成纯文字、没有调用 reply，本轮记为失败。
  原因是续答指令没有提醒结束方式；已在续答指令里写明须调用 reply。改后一次批准（新建 NOTES.md）续答正常，
  文件内容正确；一次通过不能证明不会再出现。
- 批准卡片的用途句起初是英文；工具参数说明和提示改为要求用用户的语言，之后为中文。
