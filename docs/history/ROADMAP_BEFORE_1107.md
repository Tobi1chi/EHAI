## 11-04 试用反馈

11-04 用户在桌面窗口试用后提出下列四项。同日由产品经理角色定下方案并实施第一版（[工作台与助手](WORKBENCH_ASSISTANT_DESIGN_1104.md)），下表“现状”是实施前的状态，“待定”各项的决定写在该设计文档；用户验收后再合并。

| 项 | 用户要求 | 现状 | 待定 |
| --- | --- | --- | --- |
| 1. 非 Git 文件夹一键初始化 | 添加工作区时，如果文件夹不是 Git 仓库，弹窗说明，用户确认后一键初始化 | 登记接口对非仓库返回 422（`Workspace path must be a Git worktree root`）。试用中连续失败 3 次，用户手动 `git init` 后才登记成功；登记后仓库没有提交，Run 没有执行基线 | 一键初始化是否同时建首个提交；选中的是仓库子目录时怎么处理 |
| 2. 像 Codex 那样安排权限 | Pi Agent 的权限按 Codex 的方式安排 | 按工作区逐项开放：允许的命令（`--allow-command`）、Shell、Git 权限（如 `git.read`），默认全部关闭。11-04 验收中 `ehai add` 没给 `--shell`，验收命令就没能成为 Gate | 用几档预设（只读、工作区内可写、完全访问等）及何时请用户批准；预设与执行配置指纹、已批准 Run 的授权边界怎样对应 |
| 3. 对话代替手填 | 少让用户手动输入：用户与 AI 对话，由 AI 填写内容，个人 Agent 作为用户与实际编码 Agent 之间的桥梁 | 工作台和终端会话里，文件夹、项目、目标、权限等多处要用户手填；[PRODUCT_SCOPE](../PRODUCT_SCOPE.md) 规定常驻顶层 Agent 在 EHAI 之外、经 CLI/MCP 使用核心 | 个人 Agent 放进 EHAI（工作台的对话入口），还是继续放在外部、EHAI 只提供它填写所需的接口；如需改 PRODUCT_SCOPE，先由用户决定 |
| 4. 工作台式页面 | 除了与操控 EHAI 的 Agent 对话，整个页面做成工作台：便签式卡片一眼看清各项事务，点开看细节，不再到处手动操作；注意留白，简洁明了 | 页面按生活/工作两区与线程页组织（[ADR 0008](../adr/0008-web-workbench.md)），添加文件夹、开始 Run、整合等都是各自的操作面板 | 卡片上放哪些对象（线程、待办、便签、Run）及展开方式；与第 3 项的对话入口怎样同屏；设计时用 Anthropic 官方 frontend-design skill 作美学参考 |

## P2：围绕真实项目收尾

目标：通过正常入口完成一项真实项目工作，保留批准、成果与人工回路，中断时能明确恢复依据和下一步。
已接通的 block 对应、Git 整合和后继 Run 不重复开发。

| 工作项 | 输入与预期输出 | 完成条件 |
| --- | --- | --- |
| 成果与批准接续 | 前驱 Run、明确的新批准及来源映射 → 后继 Run 和可追溯成果 | 补充多次接续和异常中断证据；失效输入不沿用旧成果或 Gate |
| handoff 与恢复 | 持久执行事实、成果和中断原因 → 正常入口可继续或明确请求人工 | 未知副作用先核对，不用新会话盲重放 |
| 有效上下文接续 | 获批目标、有效图、已验证成果、决定与未决问题 → 下一段任务输入 | 核对逻辑 Phase Session 与物理 Pi Session 的连续性；不自研压缩 |
| 产品验收 | 一项真实项目工作 → Gate、成果和控制路径可核对 | 产品 E2E 已入库；真实 Pi 按 [手动验收](../DEVELOPMENT_GUIDELINES.md#真实-pi-手动验收) 完成 |
| 加固（11-03 第 7 步） | 写入中断、长链接续；Planner 生成的重复人工 Check | 脚本化 Pi 下系统验证恢复；计划校验拒绝规范化内容相同的人工 Check |

每轮只选一个明确用户结果；只对实际阻断做必要修复，修复后重试原路径，旁支另记。

## P3：从多项目管理到日常工作台

首个产品目标：用户同时管理几个项目，让 EHAI 执行任务；回来看到成果和需要处理的事项，
处理后能确认任务继续、结束或仍在等待的真实原因。

| 阶段 | 范围与输入输出 | 所有权与失败行为 | 正常入口完成条件 |
| --- | --- | --- | --- |
| P3.1 项目总览 | 项目、目标、Run、成果和宿主关联的摘要与详情 | 核心提供查询事实；断线或旧数据明确标注，不推断完成 | 正常查询找到两个项目各自的运行与成果，归属不串项目 |
| P3.2 便签与统一待办 | 聚合人工请求；便签讨论与明确决定驱动源操作/提案/修订 | 讨论不隐式批准、扩权或解除阻塞；过期时重读 | 经 CLI/API/MCP 发起便签、处理并确认核心后续状态 |
| P3.3 薄 Web 工作台（10-06 已实现） | Home、项目详情、待办与成果；轨迹按需展开 | 只消费正式 API/生成 Client，不读库、不复制业务状态 | 在页面完成上述查看和处理，刷新后状态一致 |
| P3.4 事件消费 | 持久消费位置、确认与断线补领 | 离线不阻断核心，重复投递不重复执行动作 | 重连后处理未消费事项并核对结果 |
| P3.5 多项目配置 | 角色、Pi 运行配置与项目静态规则分开，Run 保存快照 | 配置变更不静默作用于已运行任务 | 两个项目各用自己的规则与工作区 |

多工作区管理层托管多个独立核心进程，按 workspace_id 路由并聚合；不把单个核心变成跨仓库调度器，
也不让多个 Planner 共同编辑一个计划。用法见 [多工作区后端](../WORKSPACE_MANAGER.md)。

应用外壳（10-22 方向，[设计](../APP_SHELL_DESIGN.md)）：线程读模型、本机引擎、线程式页面与 Tauri 外壳第一轮已接通；
第二轮为 `ehai doctor --probe` 与终端交互会话（11-03 第 3 步）。

页面首版优先"需要我处理 / 正在推进 / 已验证成果"。看板、甘特图、日历、自定义组件、
完整配置中心及跨项目公平调度不是首批依赖。

## P4：重复事务与外部连接

Workflow 描述固定事务怎么做，Routine 描述何时调用，Workflow Run 保存一次执行结果，
与核心的计划 Run 区分。Project 是业务归属，workspace 是执行环境；生活事务不要求 Git 或重新规划。
开放式编码、研究和修复继续交给核心计划执行，Workflow 不另建 Worker 状态机。

已接通（用法见 [WORKFLOWS](../WORKFLOWS.md)、[Connector](../CONNECTOR_PROTOCOL.md)、[实验说明](../DUAL_FEEDBACK_EXPERIMENT.md)）：

- 固定 `life.capture` / `life.review` v1、项目 Routine 和独立执行记录；版本兼容代码保持关闭。
- Connector 标准 HTTP 协议与 Google Calendar 适配器（只有本地替身证据）。
- Jev 双反馈环只读实验、固定 Pi 回退，以及向独立 Project 转交代码修改（[边界](../P4_WORKFLOW_REVISION_DESIGN.md)）。

- 自定义 Workflow 第一版（11-03 第 6 步）：定义版本与校验、条件分支、Connector 动作目录与调用收据、
  人工步骤进 Inbox、持久时间等待、Routine 绑定流程版本；只有 Connector 替身证据。

下一目标：事件/日历触发按生活场景逐个接入，先定契约和失败处理，再在授权内接真实资源。
是否需要独立 Runtime 由实际需求决定。
