| 阶段 | 范围与输入输出 | 所有权与失败行为 | 正常入口完成条件 |
| --- | --- | --- | --- |
| P3.1 项目总览 | 查询核心已有项目、目标、Run、成果和宿主关联，返回可定位的项目摘要与详情入口 | 核心提供查询事实；断线或旧数据明确标注，不能推断任务完成 | 从正常查询入口找到两个项目各自的运行与成果，无需手抄全部 Run ID，归属不串项目 |
| P3.2 便签与统一人工待办 | 聚合、Planner raise_note、持久讨论和决定驱动的源操作/提案/修订讨论入口已接通 | 讨论不隐式批准、扩权或解除阻塞；源请求、批准版本和决定均可追踪，过期时重读 | 无页面，经 CLI/API/MCP 发起便签、讨论、明确处理并确认核心后续状态，其他项目独立继续 |
| P3.3 薄 Web 工作台 | Home、项目详情、待办与成果；显示当前计划/有效分支，轨迹按需展开 | 只消费正式 API/生成 Client，不直接读库、不复制业务状态；显示请求错误及连接状态 | 在页面完成上述查看和处理，刷新后状态一致，CLI/MCP 仍可独立使用 |
| P3.4 外部 Agent 事件消费 | 基于已有事件查询/SSE，定义持久消费位置、确认与断线补领 | EHAI 保留事实，外部 Agent 自行决定响应；离线不阻断核心，重复投递不重复执行动作 | 外部调用者重连后可处理未消费事项并核对结果；不把 MCP 连接等同于自动唤醒 |
| P3.5 多项目配置 | 分清可复用角色、Pi 运行配置与项目静态规则，保留执行时的有效配置快照 | 核心校验项目/宿主/工作区与授权；配置变更不静默作用于已运行任务 | 两个项目使用各自规则与正确工作区，配置变更对新旧执行的影响可解释 |

P3.1 已提供按宿主的项目列表和详情，以及宿主当前上下文查询，见 [实施记录](P3_IMPLEMENTATION_PLAN.md)。

这不把单个核心变成跨仓库调度器，也不让多个 Planner 共同编辑一个计划。

## P4：重复事务与外部连接

当前选定实验为 [Jev 双反馈环](DUAL_FEEDBACK_EXPERIMENT.md)：Project 内显式批准的只读
配方 → Jev 判断/代码绑定 → 查询或外部 Agent 升级 → 候选回放 → 明确发布 → 纠错暂停。
实验已接通正常 API/CLI/MCP；采用独立 Jev Connector，慢环保持外部 Agent 所有权。
先验证这条有限闭环，不将其记作通用 Workflow 引擎或自动经验学习完成。

后续精简增量已把升级分支接到显式配置的 Pi 只读回退；宿主自动推进、保存回答及可选候选，
基于操作者独立验证案例触发一次复测。发布仍需明确决定，故障不自动重放模型；详见实验说明。

2026-09-25 增加独立目标 Project 的工程修改转交，复用正常编码规划/批准/执行链；
允许独立 EHAI 源码检出，禁止指向运行框架和私有状态。路径保护及最小项目真实慢环→草稿
已验证；随后同Goal通过人工修订/批准、真实候选修改/审查和人工验收，Run completed。
整仓规划收敛、重复人工检查和传输稳定性仍待处理，不能推断原生通用流程引擎完成，
详见 [Project 修改边界](P4_WORKFLOW_REVISION_DESIGN.md)。

2026-09-24 范围澄清：生活 Routine 包括订票、行程和日程提醒；下一优先目标为
自定义 Workflow 定义/版本、条件分支、人工与持久等待，以及可扩展 Connector 动作契约。
Routine 引用流程版本和输入，不再以两个固定待办流程限定产品边界。
设计、实施顺序和外部副作用恢复边界见 [自定义 Workflow 设计](P4_WORKFLOW_DESIGN.md)；尚未实现。

独立 Connector 增量已接通：主进程通过标准 HTTP 动作/结果/事件协议与外部进程通信，
Google Calendar 为首个适配器；四动作及未知结果核对已完成本地替身试用，实际账号尚未授权。
见 [Connector 协议与用法](CONNECTOR_PROTOCOL.md)。自定义分支图和事件触发 Routine 仍未实现。

先行增量：2026-09-24 按用户要求实现独立执行记录（Run、步骤、调用、等待），
并准备版本兼容接口但保持关闭。该存储/查询增量不等于通用分支或 Connector 引擎完成。

当前已实现首条生活事务流程：外部 Agent 整理原文 → 候选待办 → Inbox 明确确认 →
生活待办 → 手动/定时回顾。固定 `life.capture` / `life.review` v1 和项目 Routine
已经接通 CLI/API/MCP，非 Git 工作区的子 Agent 操作与重启试用通过，见 [P4 实施记录](P4_IMPLEMENTATION_PLAN.md)。
将 Project 的业务归属与 workspace 的执行环境分开说明；生活事务不应因沿用编码路径而
被迫要求 Git 仓库、代码补丁或每次重新规划。保留现有核心处理开放任务的能力，按实际步骤接入。

Workflow 描述固定事务怎么做，Routine 描述何时或因何调用，Workflow Run 保存一次执行结果，
与核心的计划 Run 区分；本轮只提供两个固定流程、固定时间间隔和持久回顾快照。
手动执行、结果查询、必要人工确认和定时触发已接通；自定义图、条件分支与 Connector
是下一增量，事件/日历触发按生活场景接入，开放 Agent 步骤仍需独立明确契约。
通知与业务连接器围绕该场景逐个加入，先把契约、配置和失败处理做具体，再在授权内接真实资源。
开放式编码、研究和修复继续交给核心计划执行；Workflow 不另建 Worker 状态机。
是否需要独立 Runtime 由实际需求决定，不预先复制旧项目的多进程架构。
