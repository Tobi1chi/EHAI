## 11-03 推进计划

2026-11-03 用户决定一次走完下列步骤，每步一个 PR（分支 `claude/<主题>`），按顺序执行；
步骤内的小问题自行判断，写进对应文档的执行记录。只在需要用户本人凭证或桌面操作、改动会破坏
已授权 Run 的恢复、或要删除用户数据时停下。每步合并前本地通过 AGENTS.md 列出的静态检查与产品 E2E，
API 变更重新生成 Schema 与 TS Client。

| 步骤 | 用户结果 | 完成条件 |
| --- | --- | --- |
| 1. 路线图同步 | 计划与已定决定写在一处 | 本页、[应用外壳](APP_SHELL_DESIGN.md#待决事项)、[重构计划](REFACTOR_PLAN.md#待决事项) 的待决事项改为决定 |
| 2. 小决定落地 | 错误与重放语义一致，CLI 可启动 scripted Run | 幂等键冲突统一 409 `conflict`；便签重放返回原回执；删除 `--worker-timeout-seconds`；scripted 宿主下 `--execution-config` 可选；Schema/Client 重新生成 |
| 3. 应用外壳第二轮 | 终端里完成一条线程的全程；doctor 能确认模型设置被接受 | `ehai doctor --probe`；无参数 `ehai` 进入交互会话（列线程、新建、讨论、批准开始、看进度、处理待办、整合、建分支） |
| 4. ADR 0007 第 6 步 | 新 harness 不改核心枚举 | 执行配置 `harness: {kind, version, settings}`，旧 Pi 形状可读且指纹不变；兼容层声明能力，Hub 在 `/v1/health` 汇总；Pi 配置校验移到 Hub 一侧，去掉 import-linter 过渡例外 |
| 5. ADR 0007 第 8 步 | 可用 Claude Code 执行节点 | Claude Code 兼容层经每会话 MCP 端点；事件归一化、取消、续用、权限翻译；仓库外诊断用真实 Claude Code 对接脚本化 Anthropic 兼容服务 |
| 6. P4 自定义 Workflow | 用户或外部 Agent 定义带分支、人工决定与等待的生活流程 | 定义/版本/校验与条件分支；Connector 动作目录与调用收据；人工步骤进统一待办，时间等待可恢复；Routine 引用流程版本（旧 Routine 语义不变）；用 Connector 替身走通 查票 → 分支 → 批准 → 预订 → 写日程 → 等待 → 通知 |
| 7. P2 加固 | 写入中断与长链接续有系统证据；不重复人工检查 | 脚本化 Pi 系统验证写入中断与长链接续恢复；Planner 计划校验按规范化内容拒绝重复人工 Check |
| 8. 真实验收清单 | 用户能逐项完成需要凭证或桌面的验收 | DeepSeek Planner/Worker、Claude Code 真实会话、系统通知、桌面文件夹选择器、Google Calendar 真实账号；逐项写明命令与核对点，可执行的按 AGENTS.md 记入 EVIDENCE |

### 11-03 已定的架构决定

| 待决事项 | 决定 |
| --- | --- |
| 桌面 App 凭证来源 | 只继承登录 shell 环境（现状），不做钥匙串；EHAI 不保存凭证 |
| 开 PR 是否进核心 | 不进；核心止于创建分支，推送和开 PR 归用户或外部 Agent |
| `ehai doctor` 是否启动 Pi | 是：`ehai doctor --probe` 经 Hub 真实启动一次会话，核对模型与思考级别被接受，不调用模型 |
| 终端交互会话 | 做：无参数 `ehai` 进入交互模式，基于线程接口 |
| 第二个 harness | Claude Code：原生 MCP（用 Hub 第 7 步的每会话端点），可关闭内置工具 |
| 执行配置 | `harness: {kind, version, settings}`；旧 Pi 形状继续可读、指纹不变 |
| 能力清单 | 兼容层声明，Hub 在 `/v1/health` 汇总；调度按能力匹配，不写后端名 |
| `--worker-timeout-seconds` | 删除 CLI 参数，多工作区登记中的同名字段读时忽略 |
| CLI 启动 scripted Run | scripted 宿主下 `--execution-config` 可选 |
| 幂等键冲突错误码 | 统一为 409 `conflict` |
| 便签命令重放 | 改为返回原回执，与其它命令一致 |
| 自定义 Workflow 第一版 | 有限无环单路径图；步骤为 动作 / 条件 / 人工 / 等待 / 结束；调用先存意图再发请求；Routine 绑定流程版本 |
| P5 | 不做（定义为真实使用后再立项） |

## P2：围绕真实项目收尾

目标：通过正常入口完成一项真实项目工作，保留批准、成果与人工回路，中断时能明确恢复依据和下一步。
已接通的 block 对应、Git 整合和后继 Run 不重复开发。

| 工作项 | 输入与预期输出 | 完成条件 |
| --- | --- | --- |
| 成果与批准接续 | 前驱 Run、明确的新批准及来源映射 → 后继 Run 和可追溯成果 | 补充多次接续和异常中断证据；失效输入不沿用旧成果或 Gate |
| handoff 与恢复 | 持久执行事实、成果和中断原因 → 正常入口可继续或明确请求人工 | 未知副作用先核对，不用新会话盲重放 |
| 有效上下文接续 | 获批目标、有效图、已验证成果、决定与未决问题 → 下一段任务输入 | 核对逻辑 Phase Session 与物理 Pi Session 的连续性；不自研压缩 |
| 产品验收 | 一项真实项目工作 → Gate、成果和控制路径可核对 | 产品 E2E 已入库；真实 Pi 按 [手动验收](REFACTOR_PLAN.md#真实-pi-手动验收) 完成 |
| 加固（11-03 第 7 步） | 写入中断、长链接续；Planner 生成的重复人工 Check | 脚本化 Pi 下系统验证恢复；计划校验拒绝规范化内容相同的人工 Check |

每轮只选一个明确用户结果；只对实际阻断做必要修复，修复后重试原路径，旁支另记。

## P3：从多项目管理到日常工作台

首个产品目标：用户同时管理几个项目，让 EHAI 执行任务；回来看到成果和需要处理的事项，
处理后能确认任务继续、结束或仍在等待的真实原因。

| 阶段 | 范围与输入输出 | 所有权与失败行为 | 正常入口完成条件 |
| --- | --- | --- | --- |
| P3.1 项目总览 | 项目、目标、Run、成果和宿主关联的摘要与详情 | 核心提供查询事实；断线或旧数据明确标注，不推断完成 | 正常查询找到两个项目各自的运行与成果，归属不串项目 |
| P3.2 便签与统一待办 | 聚合人工请求；便签讨论与明确决定驱动源操作/提案/修订 | 讨论不隐式批准、扩权或解除阻塞；过期时重读 | 经 CLI/API/MCP 发起便签、处理并确认核心后续状态 |
| P3.3 薄 Web 工作台（10-06 已实现） | Home、项目详情、待办与成果；轨迹按需展开 | 只消费正式 API/生成 Client，不读库、不复制业务状态 | 在页面完成上述查看和处理，刷新后状态一致 |
| P3.4 事件消费 | 持久消费位置、确认与断线补领 | 离线不阻断核心，重复投递不重复执行动作 | 重连后处理未消费事项并核对结果 |
| P3.5 多项目配置 | 角色、Pi 运行配置与项目静态规则分开，Run 保存快照 | 配置变更不静默作用于已运行任务 | 两个项目各用自己的规则与工作区 |

多工作区管理层托管多个独立核心进程，按 workspace_id 路由并聚合；不把单个核心变成跨仓库调度器，
也不让多个 Planner 共同编辑一个计划。用法见 [多工作区后端](WORKSPACE_MANAGER.md)。

应用外壳（10-22 方向，[设计](APP_SHELL_DESIGN.md)）：线程读模型、本机引擎、线程式页面与 Tauri 外壳第一轮已接通；
第二轮为 `ehai doctor --probe` 与终端交互会话（11-03 第 3 步）。

页面首版优先"需要我处理 / 正在推进 / 已验证成果"。看板、甘特图、日历、自定义组件、
完整配置中心及跨项目公平调度不是首批依赖。

## P4：重复事务与外部连接

Workflow 描述固定事务怎么做，Routine 描述何时调用，Workflow Run 保存一次执行结果，
与核心的计划 Run 区分。Project 是业务归属，workspace 是执行环境；生活事务不要求 Git 或重新规划。
开放式编码、研究和修复继续交给核心计划执行，Workflow 不另建 Worker 状态机。

已接通（用法见 [WORKFLOWS](WORKFLOWS.md)、[Connector](CONNECTOR_PROTOCOL.md)、[实验说明](DUAL_FEEDBACK_EXPERIMENT.md)）：

- 固定 `life.capture` / `life.review` v1、项目 Routine 和独立执行记录；版本兼容代码保持关闭。
- Connector 标准 HTTP 协议与 Google Calendar 适配器（只有本地替身证据）。
- Jev 双反馈环只读实验、固定 Pi 回退，以及向独立 Project 转交代码修改（[边界](P4_WORKFLOW_REVISION_DESIGN.md)）。

下一目标（11-03 第 6 步，未实现，设计见 [自定义 Workflow 设计](P4_WORKFLOW_DESIGN.md)）：
自定义 Workflow 定义/版本、条件分支、人工与持久等待、可扩展 Connector 动作契约；
Routine 引用流程版本和输入。事件/日历触发按生活场景逐个接入，先定契约和失败处理，
再在授权内接真实资源。是否需要独立 Runtime 由实际需求决定。

## P5：真实使用后再立项

11-03 决定：本轮不做。

- 经验证成果和决策的长期复用；将稳定成功方法提炼为模板、Skill 或 Workflow 建议。
  来源可追溯，启用需确认，不根据一次成功自动扩大权限。
- 生活日程、日历及更多业务连接器；不要求把每件简单事务包装成复杂计划。
- 更多执行后端、模板与扩展生态、跨项目资源策略、多设备执行。

上述候选不构成旧 Personal Dashboard 全量 PRD 的交付承诺。
