# 产品路线图

更新：2026-09-16。能力和证据见 [STATUS](STATUS.md)，旧增量见 [历史快照](history/README.md)。

先稳固执行核心，再逐步搭建个人多项目工作台。以下是优先顺序，不是日历期限，
也不代表新能力已实现；实际证据只记录在 [STATUS](STATUS.md)。

| 阶段 | 状态 | 用户结果 |
| --- | --- | --- |
| P1/P1.1 | 历史原型完成 | 目标/计划/Run、分支、Artifact、Gate、Checkpoint、CLI/API 原型闭环 |
| P2 | 可用核心初版，收尾中 | 正常项目开发、批准边界、人工回路、恢复与唯一产品 E2E |
| P3 | 下一阶段，未交付 | 多项目总览、统一人工待办、薄 Web 工作台，随后补外部 Agent 事件消费和配置管理 |
| P4 | 后续方向 | Workflow/Routine、通知与业务连接器，让固定事务在明确授权内重复运行 |
| P5 | 候选，未排期 | 生活日程、经验固化、扩展生态、更多后端、跨项目调度策略与分布式能力 |

P2 已接通 Pi 角色、并发调度、阶段 Gate、过程接口、挂起回复、CLI/HTTP、外部导入与 MCP。
顶层 Agent 在 EHAI 外，不要求另外实现内置顶层 Agent 才算核心可用。

## P2：围绕真实项目收尾

接续、handoff、异常恢复、阶段上下文与唯一产品 E2E 见 [P2 收尾计划](P2_IMPLEMENTATION_PLAN.md)。
已接通的 block 对应、Git 整合和后继 Run 不重复开发；Token/费用硬限额暂缓。
P3 可以消费现有接口，不必等待核心覆盖所有假想故障；未验证的恢复能力仍明确列出。

## P3：从多项目管理到日常工作台

首个产品目标：用户同时管理几个项目，让 EHAI 执行任务；回来看到成果和需要处理的事项，
处理后能确认任务继续、结束或仍在等待的真实原因。

| 顺序 | 范围与输入输出 | 所有权与失败行为 | 正常入口完成条件 |
| --- | --- | --- | --- |
| P3.1 项目总览 | 查询核心已有项目、目标、Run、成果和宿主关联，返回可定位的项目摘要与详情入口 | 核心提供查询事实；断线或旧数据明确标注，不能推断任务完成 | 从正常查询入口找到两个项目各自的运行与成果，无需手抄全部 Run ID，归属不串项目 |
| P3.2 统一人工待办 | 聚合干预、人工 Gate 和 Worker 请求，展示原因、证据、选项、影响与下一步 | 处理回到源对象对应的核心命令；版本过期时重读，未知结果先查询 | 查询待办并处理一个项目的问题，确认其后续状态，同时另一项目独立继续 |
| P3.3 薄 Web 工作台 | Home、项目详情、待办与成果；显示当前计划/有效分支，轨迹按需展开 | 只消费正式 API/生成 Client，不直接读库、不复制业务状态；显示请求错误及连接状态 | 在页面完成上述查看和处理，刷新后状态一致，CLI/MCP 仍可独立使用 |
| P3.4 外部 Agent 事件消费 | 基于已有事件查询/SSE，定义持久消费位置、确认与断线补领 | EHAI 保留事实，外部 Agent 自行决定响应；离线不阻断核心，重复投递不重复执行动作 | 外部调用者重连后可处理未消费事项并核对结果；不把 MCP 连接等同于自动唤醒 |
| P3.5 多项目配置 | 分清可复用角色、Pi 运行配置与项目静态规则，保留执行时的有效配置快照 | 核心校验项目/宿主/工作区与授权；配置变更不静默作用于已运行任务 | 两个项目使用各自规则与正确工作区，配置变更对新旧执行的影响可解释 |

P3.1 先核对当前查询缺口，以及项目、运行宿主和仓库的实际绑定。当前宿主执行配置包含
workspace；已有 Project 对象和同图并发不等于一个宿主已支持多个仓库的独立配置。
新增必要查询先接公开契约与 CLI/MCP，再由页面使用；具体接口在实施时按现有装配定义，
不由本文虚构命令或预设多服务拓扑。

首版优先“需要我处理 / 正在推进 / 已验证成果”。看板、甘特图、日历、自定义页面组件、
完整配置中心及跨项目公平调度不作为这三个首批交付的依赖。
这些完成条件是产品行为清单，不要求逐项新建永久测试或启动额外真实模型试验。

## P4：重复事务与外部连接

Workflow 描述固定事务怎么做，Routine 描述何时或因何调用，Workflow Run 保存一次执行结果，
与核心的计划 Run 区分；具体契约在该阶段定义。
先选一个真实重复事务，接通手动执行、结果查询和必要人工处理，再添加定时/事件触发。
通知与业务连接器围绕该场景逐个加入，先把契约、配置和失败处理做具体，再在授权内接真实资源。
开放式编码、研究和修复继续交给核心计划执行；Workflow 不另建 Worker 状态机。
是否需要独立 Runtime 由实际需求决定，不预先复制旧项目的多进程架构。

## P5：真实使用后再立项

- 经验证成果和决策的长期复用；将稳定成功方法提炼为模板、Skill 或 Workflow 建议。
  来源可追溯，启用需确认，不根据一次成功自动扩大权限。
- 生活日程、日历及更多业务连接器；不要求把每件简单事务包装成复杂计划。
- 更多执行后端、模板与扩展生态、跨项目资源策略、多设备执行。

上述候选不构成旧 Personal Dashboard 全量 PRD 的交付承诺。Skills 使用指导另行安排，
不能替代框架缺失的调度、证据收尾或恢复能力。
