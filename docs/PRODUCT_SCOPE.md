# 产品范围与职责

更新：2026-09-24。本文描述边界，[STATUS](STATUS.md) 描述实现和证据。

EHAI 是通用 Agent 平台的规划/执行核心，编码是第一个实际场景。
常驻顶层 Agent 在 EHAI 之外，通过 CLI/MCP 使用它，不需要迁入 EHAI，也不等于 Planner。

## 产品方向

2026-09-16 决议：先把执行核心用于真实项目，再逐层建设个人多项目工作台。
目标是让用户同时委托多个项目，离开后仍能推进，回来直接查看成果并处理必要决策。
衡量价值看可信成果、人工介入负担和恢复能力，不看 Agent 活动量或新增模块数量。

借鉴 Personal Dashboard（PAO）PRD v0.6、目标体验和用户流程中的以下构思：

- 项目是目标、任务、成果和执行边界；跨项目总览帮助用户找到当前工作。
- 统一“需要我处理”的入口，说明原因、证据、可选动作、影响和处理后的恢复路径。
- 结果先于轨迹：先显示已验证成果、当前进展和未决问题，原生会话与日志按需展开。
- 后续工作从有效成果、决定和 handoff 继续，减少重新解释与重复探索。
- 外部 Agent 通过事件消费连接核心；固定事务逐步由 Workflow/Routine 承接。

参考来源为旧项目 PRD §4/§14/§18/§21 和目标体验 §3；以上结论在本文自足定义，
不要求开发者访问旧仓库。旧 PRD 全量范围、代码、测试门和状态机不自动成为 EHAI 要求。
独立生活 Project 中选定的日常事务于 2026-09-23 纳入下一阶段 P4；完整日历、更多生活管理
模块和扩展生态仍为后续候选，实施顺序见 [路线图](ROADMAP.md)。

2026-09-24 开始 [Jev 双反馈环实验](DUAL_FEEDBACK_EXPERIMENT.md)：代码和 Jev 在显式批准的
只读配方目录内处理熟悉请求，外部顶层 Agent 处理升级并提出候选，回放通过后明确发布。
用户纠错暂停配方并将请求交回慢环。实验配方不替换现有定时 Routine，也不使通用 Workflow
分支、自动经验学习或外部写权限成为已交付能力。

同日后续决定允许固定 `escalate → Pi` 回退：宿主按显式配置调用只读 Pi 角色回答当前请求，
必要时提出一个候选并触发一次独立回放，发布仍须明确决定。该受限角色复用 Pi 和现有模型
容量，不改变外部顶层 Agent 的所有权，也不新增任意任务的内置 Planner。

2026-09-25 决定：慢环可把执行代码/流程分支修改交给明确绑定的独立 Project，复用该项目
现有的计划、批准、候选代码工作区和验收链。Project 可以是 EHAI 源码的独立检出，
但不得直接修改当前运行的框架/私有状态或自动部署；边界按实际运行目录确定，不按仓库名称。
用法和原生通用流程修订设计的区别见[Project 修改边界](P4_WORKFLOW_REVISION_DESIGN.md)。

## 核心与上层职责

两条入口：委托 EHAI Planner 生成方案和图，或导入外部 Agent 生成的方案和图。
绕过 Planner 不等于绕过结构校验、Gate、批准和执行授权。

| 模块 | 所有权与输入输出 | 不拥有 |
| --- | --- | --- |
| 外部顶层 Agent | 用户意图、解释、跨任务决策、调用公开能力 | 数据库状态、隐式批准 |
| Planner | 调查/讨论、方案和图、批准边界内过程提案 | 扩权、执行完成判定 |
| 计划管理 | 版本、外部导入、契约与批准关系 | 模型循环 |
| Orchestrator | 节点/分支/Gate 推进、成果与人工介入 | 用户需求重定义 |
| Scheduler | 依赖、容量、Endpoint、租约与隔离后的派发 | 方案审批、任务验收 |
| Pi | 模型调用、工具循环、原生会话与压缩 | EHAI 业务状态与授权 |
| Worker/Reviewer | 候选成果、证据、审查意见 | 自行宣布 Gate/Run 成功 |
| CLI/HTTP/MCP | 同一核心的交互与传输 | 第二套调度器 |
| 多项目工作台（P3.3 薄版已实现） | 聚合项目、运行、成果和人工待办；通过公开接口提交动作 | 核心数据库、另一套状态机、直接控制 Pi |

方案必须说明需求、范围/排除项、接口、任务输入输出、依赖、Phase/Reviewer、Gate、
权限与失败处理。批准固定需求、对外接口、Gate 和授权；批准内的过程变化可追踪进行，
改变批准边界必须回到用户决定。外部计划不能携带伪造的成功、批准或成果来源。

Pi 不是安全沙箱。EHAI 管工作区、凭证和副作用；自动 Check、人工判断、Reviewer 意见是不同事实。
详见 [执行模型](EXECUTION_MODEL.md)。

## 渐进交付边界

2026-09-22 决议：当前优先独立完成后端，页面设计与实现单独推进。
便签是问题、证据、讨论和明确决定的人机交互机制，后端归入 P3.2 的后续增量；
阻塞 Intervention 和 Inbox 是基础；便签的持久讨论、明确决定与 Planner 接入现已接通，
实际模型试用和恢复证据仍单独记录，不由接口存在推断完成。
先通过正式 CLI/API/MCP 完成业务闭环、明确公开契约，再交给 P3.3 页面消费。
P3.4 持久事件消费和 P3.5 项目规则/执行快照已独立接通后端，页面继续单独打磨。
多 workspace 管理层位于单工作区核心之上：登记并托管本机独立核心进程，统一路由和聚合查询；
每个核心保留自己的数据库、Planner 配置、Run/Gate/便签与恢复所有权。
不同 workspace 可并行规划和执行，规划容量独立限制；这不增加多个 Planner 共同编辑一个计划的机制。
这不将 P4/P5 的所有远期后端能力变为当前交付要求。

2026-09-23 后续决议：先推进独立生活 Project 的日常事务和 Workflow/Routine 后端，
完成所需架构边界后再集中开发前端。Project 表达业务归属，workspace 表达执行环境；
两者不是同一个概念，生活事务的固定步骤不以跨 Project 调度或 Git 成果为前提。
首条流程已收敛为原文/结构化事项录入、人工确认、待办管理和定时回顾；
Workflow Run 独立于核心 Run，先提供两个固定流程与项目内 Routine，见 [WORKFLOWS](WORKFLOWS.md)。
自然语言整理由外部顶层 Agent 完成；本轮不引入通用工作流编辑器或另一个模型执行循环。

2026-09-24 用户澄清：Routine 面向订票、行程和日程提醒等生活事务，不能限定为待办/回顾。
下一增量需支持用户自定义 Workflow、条件分支及可扩展外部 Connector；
Routine 负责触发流程，具体业务由步骤和 Connector 完成。先做后端，前端编辑器独立推进。
现有两个固定流程只是原型，不能作为该目标已交付的证据；设计见 [自定义 Workflow](P4_WORKFLOW_DESIGN.md)。
Connector 与主进程采用版本化 HTTP 协议分离：外部进程领取动作、提交结果和标准事件，
核心拥有调用/事件持久化和后续执行决定。Google Calendar 第一版已接通代码与本地替身协议，
不把该证据等同于真实账号集成或自定义流程引擎完成，见 [接入协议](CONNECTOR_PROTOCOL.md)。

核心保持可独立使用。每次扩展交付一个正常入口可用的小闭环，再依据真实使用决定下一步；
不要求先建齐日历、连接器、Workflow、认证和市场等全量后端才开始使用工作台。
P2 接续、恢复与总验收继续收尾；P3 可基于已有能力逐项推进，遇到核心阻断先修复原路径。
多租户、跨项目公平调度和分布式平台不作为首个工作台的前置条件。

统一待办只聚合现有人工请求，不把回复、批准、Gate 判定和恢复合并为一个隐式动作。
执行模型继续使用 EHAI 的 Run、Attempt、Phase、Gate 和 Checkpoint；旧项目的 Execution Run
不能直接等同于 EHAI Run，页面组件也不复用计划 block 的领域身份。
配置版本、持久事件消费和多工作区管理的已实现接口见 Usage/STATUS；
生活 Workflow/Routine 的精简接口和限制见 [WORKFLOWS](WORKFLOWS.md)。

先正常入口、后产品验收。HTTP 200、静态通过、字段存在和旧增量 PASS 均不等于产品交付。
唯一产品 E2E 与历史部分自举分开；实际失败的最小诊断仅在仓库外，不扩建常驻测试套件。
