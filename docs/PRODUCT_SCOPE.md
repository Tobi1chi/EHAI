# 平台定位、产品范围与架构基线

## 文档地位

本基线于 2026-09-04 按用户确认的产品讨论重整，描述目标设计，不表示这些能力已经交付。
产品定位、职责和用户流程以本文为准；阶段归属见 [Roadmap](ROADMAP.md)，当前重整顺序见
[P2 Implementation Plan](P2_IMPLEMENTATION_PLAN.md)。旧增量、ADR 和测试记录保留其历史适用范围，
不得用旧原型限制覆盖本文，也不得用历史 PASS 宣布新的产品范围已完成。

[Usage Guide](USAGE.md) 只记录已接入的入口和当前限制。产品设计、实现状态与验收证据必须分别说明；
本次文档重整不改变代码、公开 Schema 或数据库状态枚举。

## 产品定位

长期目标是一个通用 Agent 平台。EHAI 的目标、规划、审批、执行、检查、恢复和人工介入机制是其中的
核心；编码任务是当前首先做实的纵向场景，不是平台的永久功能边界。

平台应支持：

- 用户直接与 Planner 对齐需求，也可以通过顶层通用 Agent 使用平台。
- 用户审查详细方案，并借助外部 Agent 的意见决定是否批准。
- Orchestrator 根据获批方案，通过 Scheduler/Dispatcher 调用不同 Worker Agent 和外部 Agent 框架。
- 在授权范围内自动探索、重试和放弃分支；无法自主决定时挂起并请求人工介入。
- 外部服务 Connector 接收事件或执行操作，Routines 根据触发条件和预先授权复用执行核心。

逻辑分层不要求微服务拆分，也不要求现在引入所有未来角色、Provider 或插件抽象。

## 整体职责

| 部分 | 目标和输入输出 | 决策边界 |
| --- | --- | --- |
| 顶层通用 Agent | 接收用户意图，查询方案、运行和产物，协助审查、解释阻塞并调用平台能力 | 不替代 Planner 专业能力，不直接改数据库或自行批准越权操作 |
| Planner | 调查目标仓库、澄清需求、形成详细方案，根据用户或执行反馈修订 | 不执行编码节点，不分配运行时 Endpoint，不自行批准方案 |
| 方案与审批管理 | 保存版本、需求范围、验收条件、执行边界和批准关系 | 执行必须对应获批版本；不能静默更改批准内容 |
| Orchestrator | 按依赖和执行事实推进任务，处理候选、分支、检查与人工介入 | 拥有执行状态推进，不重新解释用户目标，不实现模型循环 |
| Scheduler / Dispatcher | 根据就绪任务、能力、容量和隔离条件分配 Worker 与工作区 | 不决定需求、方案优劣或任务完成 |
| Worker / Agent Connector | 把获分配任务映射为内部或外部 Agent 执行，返回代码变更、产物、事件和证据 | 只能提交候选；不能扩大范围、降低验收标准或直接完成 Run |
| Check / Gate / 交付 | 将产物与获批条件对照，决定状态，交付选中代码及证据 | Gate 严格执行条件，但不能自动证明条件本身足够 |
| 服务与事件 Connector | 接收邮件等外部输入，或发送通知、调用外部服务 | 外部内容不是授权，不需要伪装成 Worker |
| Routines / Workflow | 根据触发条件、模板和授权启动或继续任务 | 复用执行核心，不另建一套调度、完成和恢复状态机 |
| CLI / UI / 平台 API | 暴露讨论、查询、审批、执行和介入能力 | CLI、顶层 Agent、未来 UI 和 Routines 使用同一应用语义 |

顶层通用 Agent 不等于 Planner，也不要求每次对话都创建任务。方案评审可以由用户、顶层 Agent 或
外部 Agent 完成；外部 Agent 给出意见不等于平台已获批准。当前首先支持用户携带外部审查意见回到
Planner，不以前置一个完整 Reviewer Framework 作为编码闭环的启动条件。

内部模型角色复用同一 Built-in Agent Runtime，以 Prompt、Tool Profile、Context Builder、Finish Tool
和权限区分。后台执行 Runtime 管理队列、租约和并发；Agent Runtime 管理 Session、模型步骤和工具，
二者不是同一个循环。Codex 等外部框架保留其原生执行协议，通过 Agent 执行 Connector 接入。

## 当前编码主流程

1. 用户通过 CLI 提交目标，并提供用于调查的 workspace；尚无仓库时明确新项目的范围和环境。
2. Planner 在只读授权内调查代码与上下文，提出问题、记录假设，与用户逐步对齐需求。
3. Planner 返回可读的详细方案及其对应的可执行计划。用户可以审查、继续讨论或带回外部 Agent 意见。
4. Planner 修订方案；用户明确批准方案版本、完成条件和执行边界。
5. 用户通过 CLI 确认执行 workspace 并启动。规划时读取仓库不等于已获得写入授权；执行位置或关键
   仓库事实变化时，先确认方案仍适用，不在错误工作区盲目执行。
6. Orchestrator/Scheduler 调度 Worker，在隔离条件允许时并行探索，检查结果并整合选中变更。
7. 系统交付代码变更、验证结果和需求对应证据；无法自主继续时进入人工介入回路。

上述是目标用户流程，不是现有 CLI 参数说明。后台模式必须由真实运行的宿主承载；CLI 退出后任务是否
继续、如何查询和恢复，需要在实现该入口时明确，不能靠测试进程替用户维持 Runtime。

## 详细方案的最小内容

| 内容 | 要回答的问题 |
| --- | --- |
| 需求与范围 | 解决什么、不做什么、约束和偏好是什么、哪些假设尚待确认？ |
| 仓库依据与设计 | 现有模块是什么，哪些需要改变，关键接口、数据和方案取舍是什么？ |
| 执行任务 | 每项任务的输入、输出、依赖、所需能力和修改范围是什么？ |
| 探索与选择 | 哪里需要多方案，如何比较、取消和整合，哪些判断留给用户？ |
| 验收 | 每项需求用什么行为或产物证明，怎样检查，哪些需要人工判断？ |
| 授权与失败处理 | 允许自主调整和尝试到哪里，何时挂起，谁能批准变化？ |

可读方案与 PlanGraph 必须对应同一版本，不能各自维护互不校验的事实；这不要求新增第二套计划 IR。
PlanGraph 是执行表达，不等于完整需求或设计。方案固定目标、关键设计、约束和验收，Worker 保留获批
边界内的局部实现自由，不要求 Planner 预先决定每一行代码或把每次工具调用都建成 PlanNode。

Planner 可以建议完成条件，由公共构建与校验边界生成待批准的方案和契约；用户批准后才能用于执行。
任务级检查与最终交付验收分别对齐其范围；中间节点不应被迫满足尚需后续任务完成的全部最终条件。
Worker、审查者和 Planner 都不能静默降低已确认的标准；改变范围或标准必须形成明确修订并重新批准。

当前 `artifact:non-empty`、`command:exit-zero`、`semantic:required-terms` 是原型检查入口，不是通用需求
验收模型。命令通过、文件存在或词语匹配只能证明其对应条件，不能直接推出 solution 符合用户需求。
需求、设计决定、任务和验收证据应能相互对应；先形成可用的方案内容，不提前规定未经验证的数据框架。

## 执行、失败与人工回路

### 授权内自主处理

局部分支失败不必停止整个任务；仍有可行分支时可以继续、比较并剪枝。自动取消或选择必须依据已对齐的
条件、偏好和证据，不得猜测用户“品味”。局部修复与重试受预算和副作用安全约束；未知写入结果不能
通过盲目新建执行来掩盖。工具可用不等于 commit、push、远端写入等操作已获授权。

### 挂起等待人工

所有路线遇到阻塞、某步尝试耗尽、权限不足或无法决定取舍时，停止相关自动调度并保存上下文，请用户决定。
不能把“需要人的决定”一律当成不可继续的终态失败，也不能无限循环消耗预算。

介入信息至少包括：受阻任务、已经尝试的路线、失败证据、保留的产物、需要回答的问题、可选后续行动。
涉及运行中的 Worker 时，按策略收敛并保留其状态；不得只改一个展示状态而任由后台继续副作用操作。
用户回复后可继续原方案，或进入修订审批；已经完成且仍适用的成果应被保留。

“挂起待人工”在此描述产品行为，不预先规定一个已经存在的数据库枚举。现有 `paused`、失败终态、
Run/Attempt 和 Replan 限制需要结合迁移重新设计，不能用文档改名假装功能已交付。

### 修订与终止

关键设计、范围、验收或权限需要改变时，由 Planner 生成新版本并请求批准，不作为普通重试静默执行。
是否复用原 Run、创建新 Run 及如何引用既有结果，必须保留原轨迹和批准关系。
明确放弃或确定不可恢复时仍可终止；用户选择取消与系统等待用户决定是两种不同结果。

## 外部 Connector 与 Routines

Agent 执行 Connector 负责任务、Session、状态、取消、恢复和结果；服务与事件 Connector 负责外部输入
和外部操作。二者可以共享必要的凭证和权限机制，但不强行共用 Worker 生命周期协议。

P4 的目标链路为：外部事件 → Connector → Routine 条件判断 → 获授权的平台操作 → 执行核心 → 结果通知。
已有获批 Workflow/模板可按预先授权执行，不必每次重新规划或人工批准；超出授权或需要新方案时进入
规划与审批。顶层 Agent 可以参与理解事件，但简单规则不必须调用模型。

重复事件应按业务幂等规则处理，执行副作用必须可追踪。外部邮件内容不能自行授予权限；外部触发事件与
执行中产生的领域 Event 不等同，也不是所有领域 Event 都自动触发 Routine。

## 当前范围与延后范围

- 当前先打通 CLI 下“需求讨论 → 方案审查与修订 → 批准 → 指定 workspace 编码 → 验收交付”，以及
  授权内自主处理、挂起求助和继续执行。优先复用现有状态、调度、存储、Connector 和隔离能力。
- 内部 Agent Foundation 为角色和工具提供地基；通用顶层 Agent 的产品位置已经确定，但独立增量和
  交付阶段尚未固定，不把 `Assistance` 枚举存在当作交付，也不因此把完整通用交互平台塞进 P2。
- P3 提供可观察、可干预的 UI；P4 增加 Workflow、服务 Connector、事件与 Routines；P5 扩大外部
  Agent 和第三方扩展生态。CLI、Agent、UI 与 Routine 复用相同的公开应用能力。
- 本轮不要求重写全部底座，不提前实现插件市场、跨主机 Broker、分层自动派生 Agent 或完整 Workflow
  Engine。必要的新接口由真实路径驱动，而不是为未来罗列占位抽象。

## 验收与开发效率

以用户最新确认的方式为准：先实现并暴露正常 CLI/API 能力，再共同确定唯一产品 E2E。
仓库最终只保留这一条 E2E 的必要代码，不常驻 unit、integration、contract、smoke 或诊断测试。
旧测试已退役，历史结果仍可查阅，但不要求恢复。当前 E2E 尚未确定，不创建 placeholder 或把旧
固定场景改名作为最终验收。

唯一 E2E 应验证真实需求到代码的用户路径，具体步骤和断言在能力开放后确认。任务拆分、批准和执行
不能由测试代码代办；不得 monkeypatch 生产装配、预写获胜方案或答案获得 PASS。
消息落库不等于消费，产物非空不等于 solution 正确；测试仍须依据用户真正需要的结果作出判断。

正常使用或 E2E 出现失败时，先读取实际错误和证据；若需要精确定位，再在仓库外临时目录写最小单测，
通过 `uv` 定向运行。修复后回到原失败路径复测，临时定位文件不提交、不复制回仓库、不自动转成
长期回归测试，也不因一个缺陷扩建测试框架或相邻功能矩阵。

Ruff、格式检查、类型检查和生成 Client 构建继续使用，不属于新增测试套件。真实模型调用需显式授权和
隔离工作区；不无限重试、不降低验收条件。未运行或未收集到 E2E 必须如实标记，不能报告为产品通过。
这项策略取代历史增量中强制单测、专项 Smoke 和全量测试的实施要求；不改变产品运行时的 Check/Gate。

## 后续细化方式

每个模块先写清用户目标、输入与输出、调用方、状态/权限所有者、失败处理和最小验收路径，再对照现有
实现决定保留、接通或重构。顺序是：方案与批准 → Planner 交互 → Worker 输入和交付 → 人工回路 →
生产装配与 CLI 验收。未定的具体 Schema、命令名和状态迁移在对应增量落实，不在本基线伪造已实现接口。
