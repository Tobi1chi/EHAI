# Worker、阶段决策树与执行边界共识

## 地位与适用范围

## Worker 是按预设实例化的 Agent

```text
Agent 框架：Pi / Codex / 其他框架
                    ↓ 由 Agent 执行 Connector 接入
Worker 预设：职责、模型、工具、权限、运行配置
                    ↓ 按预设创建并管理
Worker：具体运行的 Agent 实例
                    ↓ 接受 Orchestrator 的任务分配
任务执行、候选成果、handoff 与执行事件
```

| 概念 | 含义与职责 | 不等于 |
| --- | --- | --- |
| Agent 框架 | 承载 Agent 运行与工具循环的执行实现，如 Pi、Codex | 模型或任务职责 |
| Agent 执行 Connector | 接入框架，提供创建、调用、观察、停止和恢复执行的能力 | 被创建的 Worker 实例 |
| Worker 预设 | 描述实例的职责、模型、工具与权限、上下文和运行配置 | 某次活跃执行 |
| Worker | 按预设经 Connector 创建、管理的具体 Agent 实例 | Connector、模型名称、任务节点或 Session |
| Planner / 编码者 / Reviewer | Agent 承担的职责，由不同 Worker 预设表达 | 只能使用某一个框架的固定类型 |
| Session | Agent 执行中的会话与上下文管理机制 | Worker 定义或任务完成事实 |

同一框架可以创建多个不同预设的 Worker；同一职责也可由不同框架承载。选择 Pi 或其他外部框架
时通过对应 Connector 接入，不为每个职责复制 Agent Loop，不再保留自研模型 Runtime。
现有 `WorkerProfile`、`WorkerEndpoint`、`Attempt`、Provider Thread/Turn 是可复用的实现基础，
但不能只凭这些对象已经存在，就认为 Worker 实例模型已经完整实现。

Worker 不与计划节点或分支强制一一对应。规划 Agent 决定任务与路线，Orchestrator 推进执行，
Scheduler/Dispatcher 根据预设、能力、容量及工作区条件调度实例；Connector 不拥有需求或 Gate 判定权。
服务与事件 Connector 仍负责邮件等外部交互，不强行视为一种 Worker。

## 计划是分阶段、带分支 Gate 的决策树

```text
目标
└─ 阶段一
   ├─ 探索路径 A → 分支 Gate A → 继续 / 修正 / 分叉 / 结束该分支
   └─ 探索路径 B → 分支 Gate B → 继续 / 修正 / 分叉 / 结束该分支
              ↓ 按方案选择或整合有效成果
           阶段 Gate 1
              ↓ 通过
           阶段二
              ├─ 路径 C → 分支 Gate C
              └─ 路径 D → 分支 Gate D
              ↓
           阶段 Gate 2
              ↓
           最终成果
```

- Phase 是计划中验收边界之间的执行阶段；阶段之间有 Gate，不再限制整个计划只有一个最终 Gate。
- 每阶段可以有多条独立探索路径；路径可以有自己的 Gate，并在验收之后继续、产生分支或终止。
  分支局部 Gate 不表示所有兄弟分支都结束或必须同步等待。
- 分支 Gate 判断该路线是否成立、能否继续；阶段 Gate 判断该阶段目标是否满足、能否进入下一阶段。
- 选择一条成功路线还是整合多条路线，以及哪些分支结果为必需输入，由获批方案明确。
  不默认要求所有探索分支都成功，也不允许把必需成果当作可选分支丢弃。
- 展示使用决策树；执行表达可以复用支持依赖、并行和汇合的 PlanGraph，不要求强行改成禁止汇合的树。
- 任务节点不等于 Gate。没有验收意义的小步骤不应各自增加 Gate，更不默认增加 lint、单测或覆盖率清单。

## 批准边界与过程调整

用户批准的底线是：**需求不变、对外约定的接口不变、Gate 不变，且不扩大已有授权。**
Planner 可以自主调整中间实现过程，包括任务拆分、依赖安排、并行与串行、实现路线及探索策略；
不能仅因这些调整涉及多个节点，就要求用户重新批准。

自主调整仍须记录依据、调整内容及其对应的批准基线，并同步可读方案与可执行计划。
不能覆盖历史方案或只改执行图，让用户看到的说明与实际运行脱节。
执行图变动不是静默更改批准内容的许可，也不是绕过阶段或分支 Gate 的手段。

需求、接口、Gate 的条件或必需性、权限需要改变时，超出上述自主调整范围，必须回到用户确认。
新增、删除、绕过 Gate 或把必需人工判定改成自动通过，不能伪装成普通实现调整。
Planner 发现目标不可实现、仓库现实与目标存在 gap 时，以便签说明受影响任务、证据、已尝试路线和
需要用户判断的事项；无法继续的相关路径暂停，独立且不受影响的路径可在授权内继续。
便签是用户可见的产品交互，不在本文假定已有某个 API 或数据库状态。

需求、可读设计、执行图和实际 Gate 必须相互一致。用户不应必须理解原型 `--criterion` 参数才能
获得正确验收条件；构建边界不能把 Planner 已提出的行为验收静默丢弃，再将不足的契约呈现为可执行方案。

### 2026-09-13：后继 Run 与最小上下文扰动

用户确认采用同一 Goal 下的后继 Run 承载新的批准边界，并要求尽量减少边界调整及反复刷新上下文。
这是后续实施约束，不表示跨批准版本接手或物理 Session 复用已实现。

- 默认在既有批准范围内推进。任务拆分、内部接口实现细节、依赖安排、算法或路线替换、重试与返工，
  只要不改变已约定的需求、对外接口、Gate 和授权，就保留原 Run；无需因过程版本变化重新批准。
- 请求边界变更时说明具体改变的已批准约定、原因及批准内方案为何不足。不能用模型不确定、
  实现困难或节点变化数量代替变更依据；也不能为了减少切换而隐瞒真正越界或扩大初始授权。
- Run 身份不是清空上下文的触发器。未受影响的阶段上下文、已确认决定、有效成果和交接继续适用；
  对受影响部分传递批准差异，并明确哪些旧指令、假设或结论失效，而不是让所有 Worker 重新调查。
- 逻辑上下文连续与物理 Session 复用分开：框架允许且角色、权限、工作区及执行归属可正确绑定时，
  可延续物理会话；需要新 Session 时通过宿主确认的有效交接传递必要上下文和证据引用。
  不强制全量回放历史，也不把无 handoff 的脏状态、过期权限或未选中分支代码作为连续性的代价。
- 后继 Run 只接手经核对仍适用的成果与未决事项。旧 Gate 证据仍归属原批准与成果版本，
  不因上下文保留而自动批准新条件；也不因产生新 Run 而重跑全部已完成工作或重置目标级预算。

正常入口验收须区分两类行为：批准内的连续过程调整不新建 Run、不仅因版本号变化重建未受影响的
上下文；真正获新批准后建立后继关系，明确传递差异与有效交接，保留原证据且不重跑未受影响成果。
具体命令、Session 绑定和接手数据结构在对应实施增量中定义。

## 自动与人工属于同一 Gate 体系

Gate 的判定可以来自自动检查、人的判断，或方案明确要求的二者组合。不能自动判定的条件交由人，
不能用产物非空、关键词匹配或 Reviewer 的自由意见冒充已经完成了必需验收。

每个 Gate 至少说明：作用范围、待验收成果、获批条件、自动或人工判定方式、所需证据、通过后的
去向和不通过后的处理。实际结果必须绑定被审查的成果版本；修改成果后不能沿用失效的通过结论。

每个阶段进入 Gate 时，由该阶段的 Review Agent 进行测试、审查，提供证据和修改建议。
Reviewer 不能自行完成整个 Run、降低 Gate、悄悄增加验收要求或替代必需的人工判断。
自动检查可由宿主执行，Reviewer 使用其结果审查；不为角色存在而重复同一套命令。
如何授权 Reviewer 调用检查、如何持久化人工决定，是后续实现内容，不在文档中伪造接口。

审查发现实现问题时，在原要求和 Gate 下修改后再验收；发现契约或可实现性问题时向 Planner 和用户反馈。
增加阶段 Reviewer 不等于恢复一套常驻开发测试。产品运行时 Gate 与仓库测试策略是不同概念。

## Phase、Session 与上下文

阶段内的任务共用 Session、共享阶段上下文；跨阶段可以新建 Session，通过明确交接携带必要信息，
避免把此前所有对话和工具输出无限累积到下一阶段。
共享内容包括目标、接口、Gate、已确认决定和有效 handoff；未选中分支的代码不得因共享上下文进入成果。
共享上下文不等于让并行 Worker 在同一个可写工作目录互相覆盖。

这是阶段级会话目标，不强制 Worker 与 Session 一一对应。具体怎样映射 Built-in Session、外部
Provider Thread 和并发执行句柄，仍待设计；不能默认“每任务独立 Thread 加一份摘要”就等于已经
实现阶段内共用 Session，也不承诺任何框架允许在一个底层 Thread 上同时执行多个任务。

## Handoff、脏状态与可恢复操作

- Worker 已提交有效 handoff：宿主确认并持久化后，可以把交接成果和上下文交给新 Session 继续。
  Handoff 包括可恢复的成果位置或版本、完成内容、必要上下文、剩余事项和已知问题，不只是口头总结。
- 没有 handoff、仅有脏状态：默认退回相关任务最近完成节点的有效成果，不把脏快照直接当成
  已确认交接继续。可以保留脏状态作为调查材料，但它不自动成为续跑基线。
- 回退按所属分支及有效上游成果确定，不是按全局最后一个完成时间回退；不得丢掉其他并行任务
  已完成且仍适用的结果。Handoff、节点完成、Gate 通过是不同事实，不能互相冒充。
- 禁止不可恢复的操作，不能只按命令名禁用 `rm` / `remove`。删除、重命名、覆盖、patch 等
  副作用路径都需要真实恢复保障；命令换名字或文件位于 Git 仓库中，不自动说明该状态可恢复。
- “先删除、稍后重建”不是成功更新的等价物，不能把中途缺失文件的风险交给下一个 Worker 猜测修复。
  未确认的外部副作用也不能因重开 Session 而盲目重放。

CLI 在本轮前台使用方式下关闭就停止执行，再打开可继续已保存的任务；长运行期间不设五六小时的
任意总超时。用户主动停止、完成、明确外部阻塞/需要人工决定是正常停止理由，既有授权与安全约束仍适用。

## 并行与模型分工

默认尽可能并行，由 Planner 给出足够细的任务条件、依赖、输入输出和隔离边界。
存在真实依赖、写冲突或容量限制时才据此串行或等待；不能把“小任务默认单 Worker”当成已确认规则。
Worker 执行明确任务，不重新承担宽泛目标的全局设计，也不代替 Orchestrator 私自调度整棵决策树。

当前用户指定的模型分工偏好：

- GPT-6 Astra：主规划及需要强全局判断、细化条件、调整路线的任务。
- GPT-5.6 Luna，max effort：不需要同等全局推理强度、主要需要遵从详细指令的执行任务。
- 阶段 Review Agent 是保留的职责，具体模型由相应 Worker 预设表达；本次未另行指定其固定模型。

这些是模型与角色的配置偏好，不是 Worker 或 Connector 的类型定义，也不是端点可用性或具体模型
别名的声明。先前 GPT-5.5 Planner / Luna high 的试用记录保留原配置，不改写为已验证 Astra。
