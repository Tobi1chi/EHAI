# 阶段 ②：富元素助手与单一队列（设计）

更新：2026-11-10。状态：**用户 11-10 批准**；M1–M3 同日实现，等用户验收（[阶段 ② 记录](records/stage2-assistant.md)）。本页是阶段 ② 的目标设计，实现状态以 [STATUS](STATUS.md) 为准。
依据：[ROADMAP 阶段 ②](ROADMAP.md#阶段)、[PRODUCT_SCOPE 第 2 节](PRODUCT_SCOPE.md#2-主线一个人一个入口很多件事)
（N4、N5、N14、E6、E46、E47、E53、E59–E61，C1、C3、S3）。11-04 版的实现已放弃，其试用发现见
[history/WORKBENCH_ASSISTANT_DESIGN_1104](history/WORKBENCH_ASSISTANT_DESIGN_1104.md)，本设计吸收其中三条：
模型常以纯文字结束而不调用结束工具；助手不知道生活区；回复里漏出内部代码。

## 1. 用户结果

- 打开首页，只有一个注意力队列：**需要你处理 / 进行中 / 已完成**，每项带“生活”或“工作”标签，跨全部工作区。
- 在首页问助手“手上的事怎样了”，得到一两句人话加几张可点的卡片（线程、待办、Gate、diff、生活待办）；
  卡片上的状态由页面按核心实时数据画出，按钮走现有接口，由用户点击。
- 助手运行在用户在 `ehai init` 选的 harness 上（Codex 或 Pi），经 Hub。

## 2. 现状（2026-11-10）

| 项 | 现状 |
| --- | --- |
| 页面 | 生活 / 工作两个分区（ADR 0008）；首页按上次分区跳转；队列逻辑在页面里（`lib/overview.ts`）由各工作区的待办拼出 |
| 生活项目 | 哪个项目算“生活”只存在浏览器本地设置里，服务端不知道 |
| 跨工作区读取 | 管理器有 `/api/v1/workspace-overview`（项目与待办）与 `/api/v1/threads`（线程，含核心推导的 `phase` 与 `next_action`） |
| 助手 | 没有。“问”页是路由实验（C4 要求移出主路径，属于阶段 ④） |
| 角色运行 | Planner、Worker、Reviewer 经 `HubRoleRunner` 在 Hub 上运行，需要一个工作目录与 ToolRegistry |

## 3. 设计选择（11-10 经用户批准）

| 编号 | 选择 | 理由 |
| --- | --- | --- |
| A1 | 队列由管理器计算，页面与助手读同一个接口；分组直接取核心的线程 `phase`，页面不再自己推导 | E46：阶段和下一步由核心推导，前端只渲染；助手与页面看到的必须一致 |
| A2 | “生活项目”移到服务端：管理器配置里保存 `{workspace_id, project_id}`；页面首次加载时把浏览器里已有的值迁过去 | 服务端的队列与助手都要知道哪个项目是生活 |
| A3 | 阶段 ② 的助手**只读**：查询工具加一个结束工具，不建线程、不记待办、不运行命令 | 完成条件只要求回答与按钮；写操作要经阶段 ④ 的统一授权原语，届时再加，避免先做一套再推翻 |
| A4 | 助手住在管理器里（`ehai up`），不进任何工作区核心；每条消息起一个新会话，把最近的对话作为上下文传入，不续用原生会话 | 助手跨工作区；不续用避免原生历史与版本问题，11-04 版这样做可用 |
| A5 | 卡片引用由服务端在回复时逐个校验存在；页面渲染时再按实时数据画，不使用回复时的快照 | S3：模型只给引用，编不出状态 |
| A6 | 首页改为“队列 + 助手”，去掉生活 / 工作分区切换；生活的待办、定时、记录页与工作的线程、项目页都保留，从同一导航进入 | C3 取代 ADR 0008 的两区 |

## 4. 模块

### M1 单一队列（管理器）

- 接口：`GET /api/v1/attention`，返回三组条目与 `observed_at`；每个条目带工作区、标签（`life`/`work`）、
  源对象引用（线程、待办或生活待办）、标题、原因、下一步与时间。不可用的工作区单独列出原因，不静默省略。
- 分组规则：
  - 需要你处理：线程 `phase` 为 `needs_attention`、`awaiting_approval`、`paused`、`failed`；没有线程归属的待办项
    （例如 Workflow 人工步骤）；已过期的生活待办。
  - 进行中：`planning`、`running`、`idle`（还没有讨论或 Run，标明“未开始”）；未过期的未完成生活待办。
  - 已完成：最近 7 天 `completed` 的线程与完成的生活待办，数量有上限。
- 生活项目：`GET/PUT /api/v1/life-binding`，保存在管理器配置；未设置时队列里没有生活标签的条目，并在响应中说明。
- 失败行为：某个工作区读失败只影响它自己的条目，不重试写操作（只读）。

### M2 助手（管理器）

- 接口：`GET /api/v1/assistant`（对话与当前状态）、`POST /api/v1/assistant/messages {text}`（跑一轮，忙时 409）、
  `POST /api/v1/assistant/reset`。对话存于 `EHAI_HOME/assistant/`。
- 运行：`HubRoleRunner`，harness 与模型取 `ehai init` 的选择；工作目录是 `EHAI_HOME/assistant/` 下的空目录；
  Codex 原生沙箱只读，原生命令与改文件请求一律拒绝；Pi 内置工具关闭。
- 工具（全部只读，最后一个结束本轮）：

  | 工具 | 返回 |
  | --- | --- |
  | `read_attention` | M1 的队列 |
  | `read_thread` | 一条线程的状态、下一步、最近的判断（取自线程时间线） |
  | `read_run` | 一个 Run 的状态、节点进度、成果摘要（commit、diff 统计、检查结论） |
  | `read_life_tasks` | 生活项目的未完成待办与最近完成的几条 |
  | `reply` | `text`（人话）与 `refs`（至多 8 个引用：`thread`、`run`、`inbox`、`diff`、`life_task`，各带工作区与 ID） |

- 校验：`reply` 的每个引用必须在当前数据中存在；`text` 不得含 JSON 对象或数组、代码块或内部代码名（如 `awaiting_approval`）。
  不合格时作为工具错误返回给模型在本轮内改正，不由服务端改写。
- 模型以纯文字结束而没有调用 `reply` 时：把最后一段文字作为不带卡片的回复送达，记录这一情况；其他故障记为本轮失败并显示原因，
  不自动重发。

### M3 页面

- 首页 `/`：左侧队列，右侧助手（窄屏助手在上）；卡片式，留白优先（E53）。
- 卡片：按引用实时读取核心数据渲染；源对象不存在时显示“已不存在”，不补造。按钮只调用现有接口：
  待办卡片用现有的待办操作（回复、人工检查、Workflow 确认）；等待批准的线程给“去批准”进入线程页；diff 卡片显示改动统计并链接 Run 成果；
  生活待办卡片有“完成 / 重开”。
- 导航：去掉生活 / 工作切换，保留各页面入口。“问”（路由实验）不动，到阶段 ④ 移出。

## 5. 不在本阶段

写操作（建线程、记待办、运行命令）；授权原语与到期通知（④）；路由实验的去留（④）；Windows 实跑；
产品 E2E 不覆盖管理器，本阶段不扩展它（理由：它启动的是单个 `ehai-api` 宿主，助手与队列在管理器里）。

## 6. 验收

- 静态检查、Schema 与 TS 客户端重新生成无漂移、页面构建、产品 E2E 通过。
- 真实验收，经正常入口（隔离 EHAI_HOME，管理器里登记两个工作区：阶段 ① 数据副本与一个有进行中 Run 的试用仓库，再设一个有过期与未过期待办的生活项目）：
  - 首页队列三组与各自的生活/工作标签正确，与 CLI 读出的线程 `phase` 一致。
  - 分别在 Codex 与 Pi（DeepSeek）上问“手上的事怎样了”：回答是人话、无 JSON，引用都画成卡片，状态与核心一致；
    在卡片上点一次真实按钮（例如生活待办“完成”、待办的人工检查），经现有接口生效。
  - 在线程状态变化后再看同一条旧回复，卡片显示新状态。
- 用户在桌面窗口试用并验收。

## 7. 执行方式

按阶段 ① 的做法经 EHAI 自身执行：Codex 作 Worker 与 Reviewer（订阅，不计按量费用），团队负责人写方案、做人工检查。
方案三个 Phase：M1 → M2 → M3，每个 Phase 有 Reviewer 与人工检查，最终 Gate 跑静态检查、漂移检查与产品 E2E。
按量费用只在 Pi 验收时产生（DeepSeek，预计远低于 ¥50）。
