## 用户结果与范围修正

Routine 面向订票、行程安排、日程提醒等日常事务，不限于待办与回顾。
用户可以自己或委托外部 Agent 定义流程，配置条件分支、人工决定和等待，并方便地加入外部服务。
先实现后端定义、执行和 Connector 契约，前端编辑器随后独立开发。

已有 life.capture / life.review 是固定流程原型和可保留的业务能力。
仅给这两个流程加默认参数，不能满足本次自定义 Workflow 要求。

## 模块职责

| 模块 | 所有权、输入与输出 | 失败行为 / 正常入口验收 |
| --- | --- | --- |
| Workflow Definition / Revision | Project 拥有；输入 Schema、步骤、连接、条件、结果及所需能力；保存不可变可运行版本 | 保存时校验节点引用、可达性、分支出口、数据引用和 Connector 契约；错误不发布，不靠执行时猜测 |
| Routine | Project 拥有；引用流程版本、输入和触发规则；产生有来源的 Workflow Run | 不拥有流程逻辑；重复触发去重，错过时间按显式策略跳过或有限补跑，不默认把回顾的合并规则用于订票 |
| Workflow Run / Step execution | 捕获定义、输入、授权及连接配置版本；记录已选分支、步骤输入输出、等待与结果 | 持久化后接续；完成步骤不重跑，未知外部效果先核对；流程记录不等于核心 Run/Worker Attempt |
| Connector | 注册动作及输入输出 Schema、凭证引用、权限、幂等/核对能力；调用外部服务并返回结构化结果 | 区分明确拒绝、可重试错误、结果未知和异步待完成；实际失败不能包装成无票或空结果 |
| 人工交互 | 绑定 Workflow Run/步骤的便签讨论、选项和明确决定，通过统一 Inbox 展示 | 讨论不自动批准；决定绑定具体参数与版本，价格/对象变化使旧决定失效；重复决定不重复派发 |

Project 表示业务归属，workspace 表示宿主执行边界。普通日常流程不需要 Git、Goal 或 Planner。
流程执行器只负责确定步骤的推进；开放推理/研究/编码任务应通过明确适配委托既有核心，
不在 Workflow 内再造 Planner/Worker 循环。当前 Pi 核心仍含代码工作区装配，
因此通用非 Git Agent 委托是后续需要明确接通的能力，不能据已有 Pi 接口宣称完成。

## 第一版自定义流程表达

后端先接收经过 Schema 校验的结构化图定义；用户可以手写，或由外部 Agent 生成并提交。
不用等待前端拖拽编辑器。以下是拟支持的步骤语义，名称和最终请求格式待代码契约确定：

- 动作：调用注册 Connector 的某个动作，或已有本地业务操作；参数来自流程输入与前序输出。
- 条件分支：使用结构化比较、字段存在性及布尔组合；必须有默认出口，第一版只选择一个出口。
  已选分支及判定依据持久化；同一 Run 恢复时不因外部数据变化重新选择已通过的分支。
- 人工步骤：提问、选择或批准具体操作，明确超时/拒绝出口；等待记录进入 Inbox。
- 等待步骤：等到指定时刻或收到与步骤关联的事件，持久保存条件、截止时间和触发收据。
  不靠长期 sleep 或保持模型 Session 运行来等待。
- 结束：返回明确业务结果，例如已预订、无合适车次、用户取消；业务无票不等于技术失败。

第一版采用有限、无环、单活动路径的图；允许条件分支重新汇合，但不提供并行分叉或任意代码表达式。
需要轮询查票时用有截止时间和次数上限的触发策略，不先增加无限循环。
将来加入并行或 Agent 步骤需各自定义取消、汇合、授权和失败行为。

## Routine 和时间

Routine 绑定特定可运行版本；更新 Workflow 不自动改变已运行实例或已启用 Routine。
手动启动不需要 Routine。触发能力分批接入：一次性时刻、固定间隔、外部事件，
以及带时区的本地日历重复规则。事件必须来自经注册/校验的来源并有去重身份。
具体规则应区分“每隔 24 小时”和“当地时间每天 09:00”，不能简单互换。

一次性提醒可由等待步骤承接；完整日历管理不是提醒能力的前置条件。
错过触发、同一 Routine 上次仍在运行、停用 Routine 时如何处理已有 Run，都需要显式契约。
首版建议默认避免同一 Routine 重叠执行；停用只阻止新触发，取消已有 Run 另行明确操作。
取消无法撤销已发生的预订或通知，退订/撤回是独立 Connector 动作及授权。

## Connector 扩展契约

宿主注册 Connector 类型及版本，Project 配置可用连接实例；流程只引用连接和动作，
不携带服务密码或 API key。动作目录应公开输入/输出 Schema 和所需能力，便于 Agent 编写流程。
新增服务时增加适配器、动作描述和连接配置，不修改 Workflow 分支调度代码。
适配器可以对接 HTTP API 或 MCP；统一传输不代表服务的业务语义、认证和恢复策略自动兼容。

动作需要描述：是否有外部副作用、调用超时、是否支持服务端幂等、如何核对调用结果，
以及是否异步返回 operation reference。凭证只能由宿主按引用解析，记录及日志需脱敏。
连接可执行范围在运行时与该次授权交集校验；修改连接目标/账号/权限后不能沿用旧授权扩大范围。

第一版需要持久调用身份和结果收据。先保存调用意图，再发外部请求，最后保存结果，
不能在 SQLite 事务中等待网络，也不能假定本地数据库事务包含外部副作用。
远端成功但本地尚未保存时：优先查询 operation reference 或同一服务端幂等键；
无法核对时保留未知状态并交给人工，不以新 key 自动重试预订/支付/通知。
支持幂等的动作重试保持同一逻辑调用身份，技术重试不等于新业务执行。

读操作可在既有读取授权内执行。预订、支付、写日历、发通知按具体动作授权：
可以使用用户明确给出的持续授权，也可在图中等待逐次确认；示例订票流程采用逐次确认。
确认至少绑定候选行程、价格/上限、对象及有效期；过期或价格改变后重新决定。

## 扩展点与兼容边界

以下补充是目标契约；动作/事件 Schema 的 HTTP 登记和独立进程协议已接通，
插件加载、自定义步骤运行或子流程能力尚未实现。
扩展目标是新增常见业务动作不修改图调度器，不意味着所有新执行语义都能靠插件实现。

| 扩展点 | 约定边界 | 首版取舍 |
| --- | --- | --- |
| Connector 动作注册 | 稳定的类型/动作身份、契约版本、输入输出 Schema、权限与核对能力；连接实例单独引用账号和凭证 | 首版宿主显式注册可信适配器；不做热加载、插件市场或任意上传代码 |
| 步骤处理器 | 校验配置、解析输入、返回结构化结果/等待请求；引擎拥有状态推进、授权、收据和事件 | 首版少量内置处理器；业务扩展优先新增动作，不为每种服务新增节点类型 |
| 触发适配器 | 将时刻、日历规则、外部事件映射为触发收据，携带来源、去重身份、发生时间、输入和流程版本 | 统一触发入口；按场景逐个实现适配器，Routine 不拥有业务逻辑 |
| 子流程复用 | 引用明确版本和输入输出契约，子流程上下文隔离，保留父子调用身份 | 预留可表达的归属和引用方式；暂不实现调用、递归或自动拼接图 |
| Agent 委托 | 用适配步骤启动/查询既有核心的任务并关联结果；核心继续拥有 Planner/Worker 生命周期 | 后续接通，不能将当前 Git 装配直接宣称为通用生活 Agent 执行 |

定义、步骤配置和动作契约要有各自的版本，运行捕获实际解析的版本和非敏感配置指纹。
兼容升级必须保留旧契约含义；不兼容变更使用新版本。旧 Run 恢复时缺少匹配适配器或契约，
应明确暂停并说明缺项，不能自动使用最新实现或将历史输出按新 Schema 强行解释。
运行中的迁移须单独设计，第一版不允许通过编辑定义改写已经选定的路径与参数。

持久化应拆分流程定义、运行、步骤执行、外部调用和等待记录；通用 Run 不携带 LifeTask 专属字段。
步骤输出使用受 Schema 约束的数据；大成果使用 Artifact 引用，凭证不进入共享上下文。
节点定义身份与该次步骤执行身份分开，避免未来重试/子流程/并行时共用一个可变 current_step。
第一版仍执行单活动路径；预留身份不是并行汇合或循环已受支持的承诺。

步骤处理器返回结果，由引擎统一保存；不获得绕过授权、改写运行状态或直接提交数据库的接口。
这是受信代码的职责契约，不是进程内安全沙箱。运行不受信插件需要另行隔离，当前不提供。
新并行、循环、补偿等控制语义必须扩展图校验、恢复与取消规则；不能伪装成普通 Connector 动作。
补偿也是独立业务动作，例如取消预订，不假定远端写入存在数据库式回滚。

扩展边界的正常验收应包含：在同一图执行器下注册另一个 Connector 动作并用于自定义流程，
沿相同记录/授权/恢复入口运行；仅新增动作实现和配置，不增加服务名称专属调度分支。
该验收围绕选定生活场景进行，不要求建永久插件测试矩阵。

## 正常入口验收场景

### 首个 Connector：Google Calendar（代码已接通，真实账号待授权）

2026-09-24 用户选择实际使用的 Google Calendar。首版已接通日历列表、按时间范围查询日程、
读取指定日程及创建一次性个人日程；创建支持明确时区和提前提醒。修改/删除、邀请参会人、
重复日程编辑及日历变更推送后续再加，不把首个 Connector 扩成完整日历客户端。

接入使用用户 OAuth 授权，凭证保存在宿主私有配置中，Project 连接绑定允许的日历。
代码完成后先读用户指定日历；写入试用需明确授权测试日历和临时事件内容。
个人弹窗提醒由 Google Calendar 的提醒设置及客户端承担，不能据 API 创建成功声明通知已送达。

创建前保存固定 event ID 和请求摘要；超时后先按该 ID 读取并核对来源/内容，
不更换 ID 盲目重建。Google 文档不保证所有 ID 碰撞都会在创建时检测，
因此采用足够随机的合法 ID 并保存核对证据，不宣称跨系统严格 exactly-once。
Connector 按注册动作接入通用调用入口，不在调度器中加入 Google 专属分支。
独立 Connector 已通过正式接口的本地替身试用，自定义图接入尚未实现。
主进程通过动作请求/结果与标准事件信封接收数据，具体字段和实际证据见 [接入协议](CONNECTOR_PROTOCOL.md)。

接口依据：[授权范围](https://developers.google.com/workspace/calendar/api/auth)、
[创建日程](https://developers.google.com/workspace/calendar/api/v3/reference/events/insert)、
[查询日程](https://developers.google.com/workspace/calendar/api/v3/reference/events/list)。

### 通用流程目标

通过公开接口保存自定义图：输入出发地、目的地、日期和预算，调用查票动作；
有票且符合约束进入选票/批准，无合适车次返回原因；批准后执行预订，
取得明确预订结果后写入日程，等待提醒时间，调用通知动作。
技术错误及未知结果走恢复/人工介入，不走“无票”业务分支。

先用隔离 Connector 替身验证自定义图、分支、等待、决定与收据；
然后按用户实际使用的票务/日历/通知服务选择一个真实 Connector，经正常入口验证其真实效果。
没有真实账号和供应商契约时，不宣称已支持实际购票。该需求澄清本身不授权替用户购买或支付。
试用由复用的子 Agent 模拟用户操作；不扩建永久单测或测试矩阵，不替代唯一产品 E2E。
